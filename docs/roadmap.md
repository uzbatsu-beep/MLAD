## Рекомендуемые следующие инженерные этапы (приоритет)

1. **P0 — оригинальные экспорты и golden fixtures.** Получить от каждого поколения хотя бы один разрешённый `CIOPRG.LST` с model/firmware/application, исходным SHA-256 и результатом OEM проверки. Гарантировать неизменность оригинала, хранение без открытой публикации, классификацию неизвестных конструкций.
2. **P0 — кодификация неизменяемости и security hardening.** Исключить доступность неподтверждённых методов `network/mod.rs` через любые будущие команды; оценить CSP, зависимости, file path/TOCTOU, атомарное сохранение JSON и резервные копии.
3. **P1 — парсер по реальным форматам.** Расширять лексические/семантические структуры по фактическим файлам; граничные условия System/User и заголовки должны быть подтверждены независимо; без известной части файл остаётся read-only.
4. **P1 — полноценная электрическая семантика.** Исправить потенциальное несовпадение офлайн-алгоритмов с точным циклом Yaskawa, добавить оставшиеся мнемоники, временные и функциональные инструкции; все предположения оформить в виде тестов и источников.
5. **P1 — UX/композиция проектов.** Проработать единый проект `graph+advanced`, историю/Undo для advanced-редактора, валидаторы и кросс-ссылки, поиск сигналов, экспорт отчёта (не экспорт native CIOPRG).
6. **P1 — воспроизводимая поставка.** Зафиксировать npm lockfile, привести CI к `npm ci`, автоматизировать новые версии тегов, подписание или доверенную политику распространения Windows, проверить WebView2 на стенде.
7. **P2 — read-only аппаратная диагностика.** Только после независимой спецификации HSES: документированные запросы, интерпретация ответов, таймауты, изоляция недоверенных данных и лабораторные проверки. Отдельно от записи и деплоя.
8. **P2/P3 — native writer и деплой.** **Не включать**, пока не готовы защищённые границы, полный verified round-trip, OEM Ladder Editor validation, отрицательные тесты, план rollback и разрешённая процедура на каждом контроллере.

## Критерии перехода к аппаратной проверке

- Имеется [матрица стендовых испытаний](advanced_hardware_test_matrix.md), но **её существование не означает, что тесты проведены**.
- Отделить локальную UI симуляцию от аппаратной процедуры OEM; не принимать JSON-проект за `CIOPRG.LST`.
- Установлены firmware, профиль memory/IO, источник копии, резервный план, неопасные тестовые сигналы.
- Перед любым реальным командным исполнением должно быть внешнее разрешение по процедуре предприятия и независимая проверка системы безопасности.

Политика PR и выпусков: [development_workflow.md](development_workflow.md).
