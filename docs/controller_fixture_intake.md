# CIOPRG.LST — приёмка оригинальных файлов с DX100/DX200/YRC1000

**Цель:** получить репрезентативные vendor-native данные для безопасного расширения парсера. **Этот процесс не разрешает загрузку программ, редактирование System Ladder и живое управление роботом.**

## 1. Что нужно от инженера со стенда

Для **каждого** поколения контроллера по возможности предоставить:

| Поле | Что записывать |
|---|---|
| Контроллер | DX100 / DX200 / YRC1000, точная аппаратная ревизия |
| Firmware / system software | Версия с панели, дата сборки при наличии |
| Application | Handling / welding / painting / иные установленные опции |
| Средства экспорта | Версия встроенного меню, Ladder Editor 32 и способ получения файла |
| Файл | Изначальный `CIOPRG.LST`, размер, точный SHA-256 |
| Тип данных | Исходная кодировка/наличие BOM, CRLF/LF/CR, признаки `//$M` |
| OEM результат | Проверялся ли файл штатным редактором/контроллером, какие diagnostics |
| Содержимое | Присутствуют ли TMR/CNT, GSTR/GOUT, PART, System/User Ladder |
| Конфиденциальность | Владение, разрешение на обработку, ограничения по распространению |
| Функциональные тесты | Отдельный стендовый протокол: что действительно измеряли, что нет |

### Определение SHA-256 в Windows

В PowerShell (файл следует считать с носителя, **не открывая его для редактирования**):

```powershell
Get-FileHash -Path "D:\\backup\\CIOPRG.LST" -Algorithm SHA256
```

Это контрольная сумма **оригинальных байтов**, не SHA от нормализованного текста. При каждом копировании сравнивайте хеши, а не имена файлов.

## 2. Безопасный рабочий порядок

1. Создать **неизменяемую** исходную копию вне рабочих каталогов. Оригинал не редактировать и не перекодировать.
2. Зафиксировать метаданные контроллера, дату и источник; имена клиентов, IP, пароли и технологические секреты **не публиковать**.
3. В `Просмотр CIOPRG.LST` выбрать точный `ControllerFamily` и открыть **копию**, не оригинал на носителе.
4. Записать хеш, число строк, ошибки, процент покрытия, список **неизвестных** мнемоник/секций, присутствие заголовка `//$M`. Факт отсутствия ошибки — не подтверждение native compatibility.
5. Отдельно сравнить с OEM редактором/выгрузкой без изменения защищённой части. Нельзя выдавать синтетический test snippet за настоящий экспорт.
6. Для тестовой фикстуры согласовать разрешённую минимальную анонимизацию. **Любая анонимизация меняет байты и SHA-256**; сохранить связь `original_hash → sanitized_hash` в закрытом реестре.
7. Использовать репозиторий только для разрешённых **синтетических** и обезличенных фрагментов с явным происхождением. Клиентские System Ladder, network configuration и секреты в публичный git не добавлять.

## 3. Golden fixture acceptance

- Содержимое и хеш файла проверяются дважды независимо.
- Проверка `parse_document` не изменяет исходных байтов (`copy_original() == input`), включая BOM и окончания строк.
- Реальные unsupported конструкции должны оставаться `opaque`; валидация не должна отбрасывать фрагменты и выдавать их за поддерживаемую логику.
- `system_user_boundaries_verified=false` и `edited_export_allowed=false` сохраняются, пока полная проверка vendor-файлов и разграничения прав не завершена.
- Тестовая фикстура должна воспроизводить именно тот случай, который она доказывает: `controller`, `fixture_hash`, `expected_diagnostics`, `parser_version`, `vendor_verification`.
- Сложные функции TMR/CNT/GSTR/GOUT и логические ветви нужно проверять на уровне *истинного* source trace, а не только локальных модельных JSON-тестов.

## 4. Приоритетные вопросы при первых реальных файлах

1. Какие поля идут **до** первого `PART` и какие обязательны по модели?
2. Как обозначены System/User boundaries и исходная длина защищённой секции?
3. Как отличаются кодировки, строки, директивы и `//$M`?
4. Что встречается между булевыми выражениями и stateful инструкциями?
5. Сохраняются ли линейные пути при `AND-STR / OR-STR`?
6. Какие инструкции и классы памяти отличаются у DX100/DX200/YRC1000?
7. Как независимый OEM редактор отображает/проверяет файл, какие сообщения выдаёт?

**На текущую дату оригинальные golden fixtures не включены в открытый репозиторий.** Отсутствие fixtures не доказывает, что у пользователя нет локальной выгрузки; это статус репозитория.

## 5. Закрытая предварительная выборка (17.11.2026)

Пять новых пользовательских выгрузок изучены локально, без передачи содержимого, контрольных сумм и конфигураций в публичный репозиторий. Наблюдаются варианты начала файла и отдельные ALARM/MESSAGE секции за `END`. На основе этого допустимо создавать **синтетические** тестовые конструкции, не содержащие реальных значений. Идентичность контроллера, firmware, права распространения и независимая проверка штатным редактором ещё не подтверждены; нельзя автоматически считать эти данные эталоном любого семейства.
