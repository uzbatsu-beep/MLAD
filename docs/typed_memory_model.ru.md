# Типизированная модель памяти CIO — DX100 / DX200 / YRC1000

> **Статус и применимость:** документ описывает ограниченное подмножество, проверенное в коде до PR #21; номер PR не означает, что разработка завершилась на этом этапе. Текущее состояние после [PR #29](https://github.com/uzbatsu-beep/MLAD/pull/29) и независимые уровни CI/UserSmoke/OEM приведены в [project_status.md](project_status.ru.md). Этот документ не разрешает native writer, HSES или моделирование фактического скана.

**Реализация:** [`src-tauri/src/compiler/memory.rs`](../src-tauri/src/compiler/memory.rs).
**Версия:** 0.1 — исходная модель адресов; соответствующая реализация в `main` проверена 18.11.2026, однако независимого OEM-допуска для конкретных прошивок нет. По таблицам нельзя выдавать разрешение на HSES-запись или deployment.
**Источники по исходной спецификации:** DX100 `RE-CKI-A453` §2, таблица 2-1; DX200 `RE-CKI-A465` §2, таблица 2-1; YRC1000 Concurrent I/O §2, таблица 2-1. См. [source_registry.md](source_registry.ru.md).

## 1. Модель адресации

Адрес отдельного битового реле CIO в канонической записи файла `#XXXXX` состоит **ровно из пяти десятичных цифр**. Последняя цифра — индекс бита в восьмибитном канале, допустимы только `0..7`. Битов с индексами `8` и `9` нет. Например, `#70017` — восьмой бит канала 7001, а `#70018` — некорректный адрес.

Префикс `#0...` должен сохранять **все пять цифр**, включая ведущие нули. Числовое представление адреса используется только как внутренний ключ и никогда не служит основанием для переформатирования защищённого исходного файла.

## 2. Точные диапазоны реле для семейств контроллеров

Обе границы каждого диапазона **включены**. Конечная цифра допустимых адресов в пределах диапазона — только 0–7.

| Класс CIO | DX100 | DX200 | YRC1000 |
|---|---:|---:|---:|
| Общий вход (CIO → задание робота) | 00010–02567 | 00010–05127 | 00010–05127 |
| Общий выход (задание робота → CIO) | 10010–12567 | 10010–15127 | 10010–15127 |
| Внешний вход | 20010–22567 | 20010–25127 | 20010–25127 |
| Внешний выход | 30010–32567 | 30010–35127 | 30010–35127 |
| Специальный вход (команда в сторону робота) | 40010–41607 | 40010–41607 | 40010–42567 |
| Специальный выход (статус робота) | 50010–52007 | 50010–53007 | 50010–55127 |
| Вход интерфейсной панели | 60010–60647 | 60010–60647 | 60010–60647 |
| Вспомогательное реле | 70010–79997 | 70010–79997 | 70010–79997 |
| Реле состояния управления | 80010–80647 | 80010–82007 | 80010–85127 |
| Псевдовход | 82010–82207 | 82010–82207 | 87010–87207 |
| Сетевой вход | 25010–27567 | 27010–29567 | 27010–29567 |
| Сетевой выход | 35010–37567 | 37010–39567 | 37010–39567 |

**Примеры, показывающие, что семейства нельзя подменять друг другом:**

- `#82010`: `PseudoInput` для DX100/DX200, но `ControlStatus` для YRC1000.
- `#87010`: недействителен в профиле DX100/DX200; `PseudoInput` для YRC1000.
- `#25010`: `NetworkInput` для DX100, но `ExternalInput` для DX200/YRC1000.
- `#37010`: `NetworkOutput` во всех трёх семействах, **не** обычный `ExternalOutput`.

Попадание адреса в диапазон **не подтверждает** наличие установленного модуля I/O и **не разрешает** системную команду. Наличие нескольких сетевых плат и распределение Ladder должны сверяться с конкретной конфигурацией робота.

## 3. M-регистры: 16-битные значения; класс ≠ право записи

Для этих трёх семейств в исходной документации указано адресное пространство регистров CIO `M000–M999` (**1000 регистров**). **Нельзя предполагать, что M1000–M3999 существуют в CIO** на основании других переменных робота или иной продукции производителя.

| Класс регистра | Диапазон | Назначение и ограничения |
|---|---|---|
| Общего назначения | M000–M559 | 16-битный регистр CIO; возможность записи зависит от инструкции и принадлежности участка программы |
| Аналоговый выход | M560–M599 | Регистр, связанный с аналоговым выходом; изменение требует проверки конфигурации |
| Аналоговый вход | M600–M639 | Результат измерения аналогового входа; обычную запись как в регистр назначения запрещать |
| Системный | M640–M999 | Значения, поддерживаемые контроллером/системой; общее разрешение на запись не выдавать |

Для каждой команды Yaskawa задаёт собственные ограничения источника и назначения. Например, регистр текущего значения таймера или счётчика может быть ограничен общими M-регистрами, даже если значение уставки берётся из более широкого диапазона.

Заголовок `//$M` использует **M480–M559**, разбитые на восемь групп в обратном порядке. Даже потенциально записываемый регистр может быть зарезервирован приложением. Значения `//$M` и принадлежность System/User необходимо сохранять, не выводя права записи по одному адресу.

## 4. Типы Rust и обязанности валидатора

```text
ControllerFamily = DX100 | DX200 | YRC1000
RelayBitAddress  = number + channel + bit + RelayClass
RelayGroupAddress = first_bit + (Byte8 | Word16)
RegisterAddress = number + RegisterClass
LadderWritePolicy = Denied | Candidate | RequiresReview
```

- `parse_relay(controller, "#70010")` проверяет ровно пять десятичных ASCII-цифр, индекс бита 0–7 и таблицу выбранного контроллера.
- `parse_register("M256")` проверяет префикс `M` и ровно три ASCII-цифры, после чего определяет класс регистра.
- `parse_group(controller, "#70010", Byte8)` / `parse_group(controller, "W#70010", Word16)` различают ширину группы. Проверяется начало на бите 0, но пока **не проверяются** специфичное для инструкции выравнивание 16-битного слова, пересечение банков и допустимые классы операндов.
- `relay_write_policy` намеренно консервативна: некоторые классы запрещены как цели `OUT`, а специальные входы управления требуют проверки. **Candidate — не разрешение на запись в оборудование**, а лишь признак, что класс потенциально может быть назначением определённых Ladder-команд.
- Принадлежность System Ladder нельзя вывести из адреса. Пользовательская программа может читать системный сигнал, не владея его определением. **System vs User** — свойство области файла/программы, а не отдельного реле.

Для обратной совместимости устаревший валидатор `validate_rungs` подразумевает YRC1000. Для DX100/DX200 вызывающая сторона **обязана** использовать `validate_rungs_for_controller(rungs, family)`. В новых вкладках UI выбор DX100/DX200/YRC1000 реализован (Graph Workspace, Advanced CIO, Inspector), но старый JSON-интерфейс сохраняет legacy-ограничения. Выбор семейства **не определяет автоматически** конкретную прошивку, установленные опции, физическое I/O и право записи в робот. Export/deployment запрещены.

## Текущее применение профилей после PR #8

- `graph_draft.rs` проверяет JSON-адреса и классы выходов относительно выбранного семейства.
- `advanced.rs` ограничивает регистр текущего значения TMR/CNT диапазоном M000–M559, уставку — M000–M999 либо 0–65535, а `GSTR/GOUT` — байтовыми группами, начинающимися с бита 0.
- `inlineOperand.ts` выполняет **только предварительную синтаксическую проверку** во frontend; контроллерозависимые диапазоны проверяет Rust. Принятый ввод не является аппаратной верификацией.
- `lossless.rs` и `semantic.rs` используют явно выбранный профиль при чтении `CIOPRG.LST`, сохраняя нераспознанные части без изменения.
- Точный model/firmware/application и ограничения физического I/O ещё требуют подтверждения реальными разрешёнными выгрузками и руководствами производителя.

## 5. Контрольный список проверки

1. Перед проверкой диапазонов выбрать семейство контроллера.
2. Проверить синтаксис и индекс бита: `#70018` / `#70019` недействительны, даже если численно попадают в большой диапазон.
3. Проверить точные границы диапазонов контроллера; пропущенные адресные промежутки недействительны.
4. Различать бит, байт, слово и регистр; `W#70010` не является битовым реле или M-регистром.
5. Учитывать специфичные для инструкции типы операндов, источник/назначение и зависимое от состояния поведение.
6. Учитывать принадлежность программы и реальную конфигурацию робота.
7. Выявлять повторные катушки, небезопасные назначения и неразрешённые инструкции.
8. Любой экспорт/деплой изменённого файла CIOPRG блокировать до независимой верификации по эталонному OEM-файлу.

Unit-тесты в `memory.rs` покрывают границы диапазонов, различия поколений, некорректные адреса, псевдовходы и сетевое I/O.

## 6. Что не подтверждено без реальных контроллерных образцов

- Права записи отдельных `SpecificInput`; общее разрешение отсутствует.
- Резервирование регистров под технологию (сварка, манипулирование и т. п.).
- Выравнивание `W#` и пересечение границ составным операндом.
- Адреса, зависящие от firmware/опций, и отсутствующие физические модули.
- Расширенные и нестандартные адресные пространства CIO для конкретных документированных ревизий.
- Полная семантика команд и разрешения портов HSES (самостоятельное заблокированное сетевое направление).
